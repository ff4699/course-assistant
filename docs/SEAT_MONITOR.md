# 独立批量课程余量监测（v0.4.0）

2026-10-13。查询、缓存与推荐由独立模块完成，没有真实选课提交能力，不改变原有选课引擎或原志愿顺序。

## 使用

打开顶部“余量监测”，每行输入一个教学班代码；可追加英文逗号与基础优先级1–5。也可以“填入当前计划”，再保存监测设置。最多5个目标，教学班代码与内部 lessonId 区分保存，不需用户找内部ID。

点击开始后，以5秒为默认目标查询间隔，可修改为5–300秒。按请求开始时间排期，一轮未完成时等待完成，不重叠、不补发错过的轮次；学校限流及Retry-After优先。查询失败保留完整旧数据，指数退避，连续5轮失败暂停。登录失效、尚未捕获真实接口或基础信息变化时停止自动请求并明确提示。重启后保留配置与数据，但暂停监测，需主动恢复。

可以暂停、停止或单轮手动刷新。手动刷新也遵守共同间隔，不绕过限流。推送使用SSE；监测面板收起只关闭推送连接，已开启的监测仍运行。可随时重开面板并暂停。

目标卡片显示名称、教学班、教师、所有时间片段、已选人数、剩余/容量、基础优先级、推荐顺序及更新时间。人数缺失不当作0，容量未知不猜测余量，旧数据显式标过期。实际响应时间由本轮测量，不写死140ms。

“当前目录人数快照”可以手动一次查询当前允许范围全部教学班；只在正常页面已经证明支持相应单批数量时启用。当前实测14个教学班，不能据此宣称全校无限数量可一次查询；实际更大范围需要新的正常页面证据。

## 当前学校事实

- 同一正常登录 BrowserContext 实际观察到 `GET /course-selection-api/api/v1/student/course-select/std-count`。
- 参数 `lessonIds` 放在查询字符串，多内部ID用英文逗号分隔。完整URL及认证头由正常请求在内存中捕获，不在代码中拼猜路径或认证；每轮重新从该浏览器读取有效Cookie。
- 响应 `result=0`，`data` 为内部lessonId到 `数字-数字-数字` 字符串的映射。第一段与页面已选人数一致；其余两段含义尚未核实，未参与计算。
- 默认可选筛选观察10个；用户正常页面“查询”后无该筛选的当前范围14个、1页。两个正常选课标签页同时存在，读取优先跟随最近正常查询的页面，避免优先读取旧标签页。
- 5个内部ID合并一次HTTPX请求成功，响应完整、人数与可见页一致，本次1845ms。
- 正常页面已经发出14ID批量查询后，HTTPX单次14ID请求也完整成功，14条人数与原页面逐项一致，本次2253ms。后续客户端复用TCP/TLS连接，延时随负载和网络变化。
- 校验过程中用户计划保持一致，没有选课提交，没有清除任何Cookie或Profile。原浏览器在本轮开始时已关闭，因此仅正常重连一次原固定Profile；用户完成人工验证后，全部实测复用这一上下文。

## 数据与独立消费者

仍使用既有SQLite Store，`school:catalog`保存课程基础信息。只有找不到教学班或用户要求重新采集时，配置操作调用已核实的课程目录读取；人数轮询仅查本机基础缓存，发现ID/学期/批次变化会要求重新确认。

`school:seat_monitor`保存目标课程副本、基础优先级、人数记录、更新时间、状态及配置；`school:catalog_seats`保存全目录人数快照。没有Cookie/Token/密码。更改目标可复用同范围快照，保留其原更新时间，不能重新包装成实时数据。

`GET /api/seats/recommendations?mode=school`提供目标状态与独立推荐顺序。各目标的顶层人数和course中的人数一致，需检查`eligible`、`stale`、`status`、`updated_at`及`count_source`后使用。它不会修改`school:plan`或调用提交接口。选课模块仍须按自己的规则确认资格、冲突、提交及核验。

可配置基础优先级优先或少量余位优先；满员、已成功、时间冲突/未知、人数未知及过期状态不进入可用推荐。两类真实时间冲突继续复用现有分析；已有课表的未知时间仍需核实。

接口：GET `/api/seats`、PUT `/api/seats/settings`、POST `/api/seats/start|pause|stop|refresh`、GET `/api/seats/events`、GET `/api/seats/catalog`、POST `/api/seats/catalog/refresh`，均支持mode，变更操作沿用本地客户端与同源校验。
